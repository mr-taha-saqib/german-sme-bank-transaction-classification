# Final Report: German SME Bank Transaction Classification

Academic proof of concept for a bachelor's thesis, implementing the pipeline of
*"Categorising SME Bank Transactions with Machine Learning and Synthetic Data
Generation"* (Aluffi et al., 2025, arXiv:2508.05425) for German transaction text.

> This project does not reproduce the paper. Language, label set, data source,
> split methodology and evaluation scale all differ. §14 sets out exactly how.

Documentation map: [`PROJECT_INDEX.md`](PROJECT_INDEX.md).
All figures below come from `results/final_results.csv`, regenerated by
`final_evaluation.py` from raw saved logits.

---

## 1. Objective

Classify short German bank-transaction descriptions into 37 categories; measure how
trustworthy the model's confidence is; and route predictions below a 0.8 confidence
threshold to human review.

The deliverable is a *scientifically defensible measurement*, not a good number. Scope is
deliberately narrow: no ERP integration, receipt matching, web application, database, API
or authentication. The pipeline runs locally and offline, and requires no credentials.

---

## 2. Dataset

Primary: `data/synthetic_b2b_transactions_2000.xlsx`, the only file with real
labelled transactions. Despite the extension it is a single-column sheet holding 65
semicolon-delimited fields per row; all 2 000 rows split cleanly into 65 fields.

| Property | Value |
|---|---|
| Transactions | 2 000 |
| Columns | 65, 40 informative, 25 constant |
| Categories | **37** (11 parent categories) |
| Class imbalance | 240 → 9 = **26.7×** |
| Distinct raw descriptions | 1 444 |
| Descriptions mapping to >1 category | **0**, labels perfectly consistent |
| Missing values in used fields | **none**. `description`, `categoryName`, `parentCategoryName` are 100 % populated |

The four LLM-generated CSVs are not merged into the evaluation data. Only
`final_synthetic_clean_7033.csv` is used, as training-set augmentation, because it is
the only one carrying `source_text` provenance that allows leakage to be excluded
mechanically. Per-file reasoning: `DATA_PIPELINE.md` §1.

The decisive structural finding: the data is template-generated
(`Software Lizenz 2024-09`, `Software Lizenz 2025-02`, …). After cleaning, 2 000
transactions collapse to 184 distinct texts. The effective sample size is the
pattern count, not the row count.

## 3. Preprocessing

Fourteen numbered deterministic transformations (`src/preprocessing.py`), deliberately
conservative. Remove only what is provably uninformative.

| Removed | Kept |
|---|---|
| ISO and German dates | vendor names |
| Invoice/reference codes (`RE-2024-8096`, `INV12345`) | legal forms (`GmbH`, `AG`) |
| IBAN-like tokens | domain terms (`ref`, `beleg`, months) |
| Standalone digit runs ≥ 3 | short numbers (`Milestone 2`) |
| | protected alphanumerics (`B2B`, `365`, `Q1`, `24/7`) |

German-specific handling: umlauts and `ß` preserved throughout; 18 unambiguous banking
abbreviations expanded (`mwst`/`ust` → `umsatzsteuer`, `sozialvers` →
`sozialversicherung`). Empty results become `nodescription`, 0 rows on this data.

Measured effect: 1 427 distinct raw → 184 distinct cleaned; vocabulary 1 083 → 175;
911 token types removed, overwhelmingly dates and reference codes.

The correction that matters most relative to the client's prototype: its cleaner deleted
every digit unconditionally, turning `B2B` into the bigram `b b`: a token then shared by
three unrelated categories, i.e. a manufactured spurious feature.

Preprocessing rules were fixed from schema and raw-text syntax before any split existed.
No rule references a label, a split or any test outcome.

## 4. Grouping

Two deterministic, label-free stages: a canonical sorted-token key, then a union-find
merge of keys at token-Jaccard ≥ 0.60.

The threshold was measured rather than assumed:

| Jaccard ≥ | Pairs | Cross-category |
|---|---|---|
| 0.9 / 0.8 / 0.7 | 0 | 0 |
| **0.60** | **61** | **0** |
| 0.50 | 168 | 7 |

0.60 is the highest threshold capturing real near-duplicates (chiefly milestone-numbered variants such as `1 automation milestone projektabrechnung` vs `3 automation milestone projektabrechnung`) while merging nothing across a category
boundary. 0.55 gives an identical grouping, so it sits on a plateau.

184 canonical keys → 152 groups, 0 label-impure. The target label is never used
to form groups; purity is verified afterwards, and a unit test asserts that permuting the
label column leaves the grouping bit-identical.

*Limitation:* grouping is lexical, so `gehaltslauf` and `payroll sammelüberweisung` (same meaning, disjoint vocabulary) stay separate. Conservative for correctness, but it
makes the split harder than semantic grouping would.

## 5. Leakage prevention

Groups are the atomic unit. A group lives in exactly one split and is never divided.
Per category, over its distinct groups with a seeded shuffle: ≥ 3 groups → 1 test,
1 validation, rest train; 2 groups → 1 test, 1 train; 1 group → train only.

| Split | Rows | Groups | Classes |
|---|---|---|---|
| train | 1 093 | 103 | 37 |
| validation | 228 | **16** | 16 |
| **test** | 647 | **33** | 33 |

Before splitting, 32 rows the source system itself flags as duplicates are removed.
26 of those 32 duplicate groups link rows with *different* descriptions (`Software Lizenz
2025-02` / `SaaS Subscription 2025-02`, same amount, same category): a leak that text
grouping alone cannot see. Removal was chosen over merging because merging cost six
additional categories their only testable group, while removal costs 32 of 2 000 rows and
leaves group structure untouched.

Vendor identity was tested as a leakage unit and rejected on evidence. Text groups and
vendors cross-cut heavily (124 of 184 text groups span >1 vendor); taking their connected
components collapses the dataset to 22 groups with 36 of 37 categories reduced to one
group, making any split impossible. Decisively, the model's only input is `description`.
Vendor fields are never fed to it, so vendor identity has no leakage channel.

Verified: 0 shared groups, 0 shared cleaned texts, 0 same-label near-duplicate pairs
across all three split pairs. 19/19 dataset checks pass.

The split is frozen with a SHA-256 (`f715f040d8a5daa6…`). Training loads and verifies
it rather than recomputing. This is what guarantees both models see identical data.

A 4-way train/validation/calibration/test split is not affordable: only 13 of 37
categories have ≥ 4 groups. Validation therefore doubles as the calibration set, which is
sound only because no model selection consumes it (§7).

## 6. Augmentation v2

No new generation is performed. The shipped LLM corpus passes three gates:

| Gate | Rejects | Dropped |
|---|---|---|
| **A** provenance | `source_text` resolving outside training | 2 483 |
| **B** collision | text equal to / sharing a group key with a held-out pattern | 0 |
| **C** near-duplicate | text reaching Jaccard ≥ 0.60 against a held-out pattern | **9** |
| | **7 033 → 4 541** | |

Gate C was added after Step-3A verification found 9 synthetic rows that were
near-duplicates (Jaccard 0.667) of two held-out test patterns. `maintenance support`
and `office supplies`. The causal path was innocent (the generation prompt carries one
training `source_text` and its category, nothing else), but by the project's own grouping
definition those training rows and those test items were the same leakage unit.

Honest outcome: removing them changed no prediction. Both affected test groups
remained correct and 0 of 33 groups flipped, so the earlier figure was not inflated. The
correction was still right (the guarantee now holds), but it should not be presented as
having fixed an inflated score.

Corpus v2 is frozen with its own checksum (`4eb242d9f384041f…`) and loaded, not rebuilt.
Combined training corpus: 1 093 real + 4 541 synthetic = 5 634 rows, 29 of 37
categories with synthetic support. 11/11 augmentation checks pass.

*Limitation:* the corpus increases class imbalance (67.5× → 89.7×), the opposite of
the paper's inverse-frequency intent, because the 8 unsupported categories are among the
larger real classes.

## 7. GermanFinBERT methodology

Checkpoint: `scherrmann/GermanFinBert_FP`. The model the client's notebook loads
(cells 53, 88) and the only German BERT in the project. The `scherrmann` family publishes
more than one artefact; `_FP` ("further pre-trained", a `BertForMaskedLM` over
`deepset/gbert-base`) is both what the notebook specifies and the correct choice, since it
carries no task head. Tokenizer: `BertTokenizer`, vocab 31 102, cased; 110.0 M
parameters; fresh 37-class head.

| Item | Value |
|---|---|
| Learning rate | 2e-5 |
| Batch size | 16 (configurable with gradient accumulation) |
| Max sequence length | 128 (p95 token length is 15, nothing truncated) |
| Epochs | 3 |
| Optimizer / scheduler | AdamW (wd 0.01) / linear warmup 10 % → linear decay |
| Loss | class-weighted focal loss, γ = 2.0 |
| Model selection | **`fixed_epochs`, none** |
| Device | `cuda:0` RTX 3060 12 GB, torch 2.13.0+cu126 |

The paper's weighted focal loss was reproduced exactly, in the mathematically correct
form `L = −α_t(1−p_t)^γ log(p_t)`. Not the prototype's `p_t = exp(−CE_weighted)`, which
is only equal when the class weight is 1. A controlled cross-entropy variant (γ = 0)
differed by one test pattern, i.e. within noise, so fidelity to the paper costs nothing
measurable. The choice was fixed a priori; the control documents sensitivity and was not
used to select the configuration.

`fixed_epochs` is a deliberate trade-off. Selecting the best epoch on validation would
likely have helped, but it would consume the validation split that Step 5 needs as an
untouched calibration set: the exact double-use mistake the audit found in the prototype.
Validation metrics are recorded for monitoring; no configuration depends on them.

One friction: the checkpoint is cased, but preprocessing lower-cases for consistency
with the already-lower-cased corpus, so German noun capitalisation is discarded.

## 8. Standard FinBERT methodology

Checkpoint: `ProsusAI/finbert`, the paper's model (Table 3) and the notebook's
comparison model (9 cells). `BertForSequenceClassification` with a 3-class sentiment head
that is discarded; tokenizer vocab 30 522, uncased; 109.5 M parameters.

Everything else is identical to GermanFinBERT, same frozen split, corpus v2, label
mapping, loss, optimiser, schedule, seeds, metrics and threshold. `compare_models.py`
refuses to produce a table unless all runs agree, verifying 12 hyperparameters plus split
checksum, corpus checksum, label mapping and test-group ordering. All 10 runs passed.

No model-specific tuning of any kind was introduced. Both models receive an
identically-initialised fresh 37-class head, so neither is advantaged by the replacement.

## 10. Temperature scaling

Fitted per run on validation logits only, then applied unchanged to test. Test labels
were never used to fit or select a temperature. Each seed calibrated independently.

Fitted temperatures: GermanFinBERT `T = 1.1012 ± 0.0798`, FinBERT `T = 1.0894 ± 0.1083`.

| Quantity | Outcome |
|---|---|
| **Validation NLL** (the fitted objective) | improved in **10 of 10 runs** |
| **Test NLL** | worsened in **6 of 10** |
| **Test ECE** | worsened in **7 of 10** |
| **Confidence stability** | worsened, ≥0.8 coverage sd rose 5.67 → 19.24 points |
| **≥0.8 coverage** | fell 60.61 % → 44.24 % (GermanFinBERT); unchanged at 0 % (FinBERT) |
| **≥0.8 accuracy** | rose 0.8022 → 0.8634, on fewer and less stable predictions |

Reported as an experiment that did not generalise, not as an improvement.

The cause is diagnosable. The calibration set holds 228 rows but only **16 independent
groups** covering 16 of 37 classes, with very unequal group sizes. Fitting the same
temperature on one averaged observation per validation group instead of per row gives a
different answer, and **in 8 of 10 runs the two fits disagree about the direction of
miscalibration**: every group-level fit says sharpen (`T < 1`), most row-level fits say
soften (`T > 1`). A calibration set on which two defensible fitting choices disagree about
whether the model is over- or under-confident does not carry enough independent
information to calibrate anything.

Accuracy, macro-F1, weighted-F1 and top-2 are bit-identical before and after. A scalar
temperature is monotone in the logits and cannot reorder predictions; this is asserted in
code for all 10 runs.

## 11. Confidence threshold

The 0.8 threshold was fixed throughout and never adjusted to improve any model's
coverage.

|---|---|---|---|---|
| germanfinbert | uncalibrated | **60.61 ± 5.67 %** | 39.39 % | 0.8022 ± 0.0335 |
| germanfinbert | calibrated | 44.24 ± 19.24 % | 55.76 % | 0.8634 ± 0.1049 |
| finbert | uncalibrated | **0.00 %** | **100 %** | undefined |
| finbert | calibrated | **0.00 %** | **100 %** | undefined |

FinBERT's maximum confidence across all five seeds is 0.7766 uncalibrated, and lower
after calibration. It never reaches the threshold on any seed in either state.

Roughly one in five automatically-processed transactions is misfiled. That is the
number a deployment decision rests on, not the headline accuracy. Confidence ≥ 0.8 is a
routing heuristic, never a correctness guarantee.

## 13. Error analysis

Across 33 test groups and 5 seeds, using each model's modal prediction:

| | Count |
|---|---|
| Both models always correct | **17** |
| Both models always wrong | **8** |
| GermanFinBERT better | 5 groups |
| FinBERT better | 3 groups |
| Tied | 25 groups |

Direction of money is the dominant failure mode. 86 % (12 of 14) of GermanFinBERT's
errors cross a *parent*-category boundary, and most are near-synonym pairs separated only
by whether money flows in or out:

* `Versicherungen` (premium paid) ↔ `Versicherungsleistungen` (claim received)
* `Dividenden / Ausschüttungen` (paid out) ↔ `Gesellschaftereinlagen` (paid in)
* `Boni / Prämien` (staff bonus, expense) ↔ `Boni / Provisionen` (commission, income)
* `software license revenue`: licence revenue, classified as the licence expense
  class `IT & Software`

The `amount` column resolves this by its sign, sits unused in the source workbook, and is
excluded by the agreed text-only scope. It is the single cheapest improvement available.
Though it would separate 8 of 13 errors, not all of them.

Ambiguous descriptions. `cloud hosting` → `Abonnements` and `serviceeinsatz technik` →
`Wartungsverträge` are defensible readings; three words cannot always separate a service
call from a maintenance contract.

Rare categories. `Boni / Prämien` has 3 training rows and is never recovered. But
scarcity is not the whole story: `cloud hosting` fails with 135 training rows for its
class and `gehaltslauf` with 78. Those are semantic confusions, not data starvation.

German-language effects. English FinBERT fragments German text ≈23 % more heavily
(3.13 vs 2.54 subtokens per word; neither model emits `[UNK]`). The clearest
German-specific wins for GermanFinBERT are `office supplies` (5/5 vs 1/5) and
`firmenwagen leasing anzahlung` (5/5 vs 1/5, FinBERT predicting `Kapitalerhöhungen`: a
compound it evidently cannot decompose). FinBERT wins on
`rechnung produktverkauf bestellung` and `hardware einkauf maschine a12`, both containing
English or alphanumeric tokens.

Grouping limitations. Every test category holds exactly one group, so per-class recall
can only be 0.0 or 1.0. Four categories cannot appear in test at all. Yet two of them are
*predicted* as confusions, so they generate false positives while being untestable.

Model-specific errors. The models disagree on only 8 of 33 groups, and neither
dominates. Their errors are largely the same errors.

## 14. Comparison with the academic paper

This project does NOT reproduce the paper. The experiments differ in ways that make
the numbers non-comparable.

| | Paper (Aluffi et al., 2025) | This project |
|---|---|---|
| Language | **English** | **German** |
| Categories | **11** | **37** |
| Data | real Open-Banking transactions, 9 SMEs | **synthetic, template-generated** |
| Independent test items | thousands of rows | **33 groups** |
| Calibration set | drawn from two full companies | **16 groups**, 16 of 37 classes |
| Split unit | held-out company (SME 3) | **held-out text group** |
| Primary model | FinBERT | **GermanFinBERT** (FinBERT as comparison) |
| Training set | balanced synthetic only | real + gated synthetic |
| Calibration | `z/T + b`, per-class bias | **scalar `T` only** |
| Standard accuracy | **73.49 % ± 5.09** | **64.85 % ± 2.71** (group) / 45.13 % (row) |
| High-confidence accuracy (>0.8) | **90.36 % ± 6.52** | **80.22 % ± 3.35** |
| Top-2 accuracy | **89.63 % ± 4.51** | **75.76 % ± 2.14** |
| ECE after calibration | **0.0048** (from 0.1091) | **0.2100** (from 0.1754. Worsened) |
| Calibration effect on accuracy | **+5.4 points** | **0.0 by construction** |

Two differences need stating explicitly.

The paper's calibration raises accuracy; ours mathematically cannot. A scalar
temperature is monotone and cannot reorder predictions. The paper's `Calibrate(·)` is
`z/T + b` with a learned per-class bias vector (§3.1.5). The bias is what moves the
argmax. That variant was tested here and drove calibration NLL to exactly 0.0000 by
fitting 38 parameters to 16 independent points, so it was excluded as over-fitting.

The paper's ECE improvement is not reachable at this calibration-set size.
0.1091 → 0.0048 on a calibration set drawn from two full companies is a different regime
from 16 groups covering 16 of 37 classes.

The pipeline follows the paper's *method* (Clean, Group, Generate, Finetune with weighted focal loss, Calibrate) and the shortfall against its numbers is explained by the data,
not by a departure from the methodology.

## 15. Limitations

1. **n = 33.** One test group is worth 3.03 accuracy points; the model gap is 1.2 groups.
   A 95 % CI on a single group-level accuracy of 0.65 spans roughly ±0.16, more than
   four times the observed gap.
2. **Every test category holds one group**, so per-class recall is 0 or 1 and macro-F1 has
   high variance. 4 categories cannot appear in test at all.
3. **The calibration set has 16 groups covering 16 of 37 classes**, the direct cause of
   temperature scaling failing to generalise (§10).
4. **Seed variance is not test-set variance.** Five seeds establish robustness to
   initialisation only; all runs share one test set.
5. **The data is synthetic and template-generated**. 2 000 rows collapse to 184 distinct
   texts. Real German SME descriptions are noisier and less consistent.
6. **8 categories have no synthetic support**, and augmentation *increases* class
   imbalance (67.5× → 89.7×).
7. **All text is lower-cased**, discarding German noun capitalisation for a cased model.
8. **Metadata is unused**. `amount` would resolve 8 of 13 observed errors by its sign.
9. **No hyperparameter search.** Configuration comes from the paper; nothing was tuned on
   validation or test.
10. **Grouping is lexical**, so semantically identical but lexically disjoint descriptions
    stay in different groups.

### What can and cannot be concluded

Under the experimental conditions and test set used in this proof of concept:

*Can be concluded*, under identical data, configuration and evaluation, GermanFinBERT
outperformed standard FinBERT on every aggregate metric and every seed; the gap in usable
high-confidence coverage (60.6 % vs 0 %) is categorical rather than marginal; LLM
augmentation is the dominant driver of performance (+27 accuracy points over no
augmentation); and the pipeline is leakage-free by construction and verified.

*Cannot be concluded*, that GermanFinBERT universally outperforms FinBERT; that the
3.6-point accuracy gap generalises beyond this test set; that any per-class result is
reliable; that temperature scaling is useless in general, only that it fails on a 16-group
calibration set; or that these results transfer to real German SME bank data.

    python train_model.py --model $MODEL --augment --augmentation-version v2 \
        --seed $SEED --output-dir results/step4_comparison \

external services are required.
